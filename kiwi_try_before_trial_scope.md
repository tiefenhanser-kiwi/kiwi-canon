## 1. What it is, in one paragraph

A visitor on `kitchenwizard.ai` goes through the wizard exactly as in the app — *"it's the wizard flow with the user choosing how they want to build plans"* — watches Kiwi assemble plan candidates **from the catalog**, opens one, reads the plan and its full recipes, **without an account**. Every write-shaped action is a door to sign-up, and sign-up keeps what they made. It is the app's own first-run arc, moved in front of the account wall, on the web.

## 2. What exists

- **The web surface exists.** Hans ran the Expo web-export probe (written August, run September 24): *"the web probe worked… not optimized, but close"* — and walked the flow: *"preferences ⇒ choose ⇒ create plan, view meal details."* Same code as the app; the auth layer already uses `sessionStorage` on web (row 3b).
- **Server pieces the guest lane reuses:** the spend guard (per-user and global ceilings), the wizard routes and limiters, the shelf and the plan-candidate contract, `LLMCallLog` with a nullable `userId`, template featuring (`featuring.ts`), the first-run gate on `firstPlanCreatedAt`.
- **What does not exist:** a session without a `User` row; a per-IP limiter for anonymous traffic; a bot check; the claim at sign-up; CORS for a web origin on Cloud Run (Phase 0 reads it); a hosted build of the export; an unauthenticated read of a featured plan.

## 3. The design — RULED (Hans, September 24) unless marked proposal

**3.1 Guest sessions, server-issued, many at once.** `POST /guest/session` → a short-lived token (`purpose: "guest"`, 24 h) after a bot check (Cloudflare Turnstile, free, web-only). A `GuestSession` row holds the preferences and the ids of what was generated. Stateless tokens: **any number of concurrent guest sessions** (Hans: *"anticipate there could be multiple concurrent sessions"*). `requireGuestOrAuth` guards ONLY the whitelisted routes below.

**3.2 What a guest can do:**
- Fill the wizard — *"same app flow and required fields… users can skip most of it if they want."*
- **ONE generation, CATALOG-ONLY.** 🔴 **Hans's ruling, and the cost decision: guest plans are assembled from catalog meals; the AI-fallback engine (D-WS9-238, the path that INVENTS meals at ≈ $0.06–0.075 and 30–40 s each) is OFF for guests.** What remains is the selection/composition call — the September 4 measurement put one catalog-based regeneration at **≈ $0.12**, so the $25/day ceiling (3.5) is ~200 guest generations, not thousands. Hans's framing, verbatim: *"as long as it's not a bot I can handle the server and AI selection costs."*
- **Thin shelf → a door, not a fallback.** When the catalog cannot meet the guest's preferences, the screen says (Hans's shape): *"Access to the full Kiwi meal library and meals that meet unique dietary needs and preferences is available in the app — sign up here."* No invented meals for a *"vegan African-cuisine-loving cilantro hater"* who will never cook them.
- Open candidates and Plan Review; open a meal and **read the full recipe and its cook steps** — *"I think it's fine to read the full recipe in the plan."*

**3.3 The doors — every action.** Grocery list · Order Online · save / edit / swap / add meals · prep and cook · a second generation · playlist · anything under Profile. Each *"no-ops and tells the user to save the meal and sign up."* **The door sheet names what sign-up unlocks** (Hans): *"download the app or create an account to use this plan, grocery list, order online, add your own meals, use Prep & Cook hub, and customize…"* — one shared component, one copy source.

**3.4 The claim.** Sign-up (and sign-in) accepts an optional `guestSessionId`. In one transaction the server copies the guest preferences to `UserPreferences`, re-parents the generated candidates / chosen plan to the user (fork-on-acquire — the shelf's own mechanism), stamps `firstPlanCreatedAt`, marks the session claimed. The user lands on the same Plan Review, every button live.

**3.5 Spend and abuse.** Per guest session 1 generation · per IP 3 sessions/day · **a separate $25/day guest ceiling under the spend guard with its own kill switch** (Hans: *"if I'm hitting that regularly and getting a lot of signups, great. if I'm hitting that and no signups, I can kill it before it hurts much"*) · Turnstile on session creation · no guest route accepts free text beyond what the wizard already allows · `GuestSession` rows and unclaimed guest plans expire after 7 days (a guest plan never becomes catalog) · guest generations are marketing cost.

**3.6 Surfaces and hosting.**
- **Guest surface = the wizard and everything downstream of it** (candidates → Plan Review → meal detail), *"not wrapped in the app experience"* — the export starts at a `/try` entry with the tab bar hidden.
- **After sign-up on the web the user is NOT interrupted:** *"they should be able to create an account on the website and go to their web-authenticated browser view of their stuff"* — the tabs appear, the same app. **Strongly encourage the app** (a persistent "Get Kiwi on your phone" strip, and the reminder in the welcome email) — cooking happens in the kitchen.
- Hosted on Netlify at **`app.kitchenwizard.ai`**; Cloud Run gets a CORS allow-list for that origin.
- **The marketing site** stays the marketing site — *"a top-right kinda Login / Signup prominent action… hard sell on getting a trial started."* Its primary CTA becomes the try flow.

**3.7 The weekly featured plan on the website (Hans, September 24 — NEW, rides this row).** *"I want to update the website regularly by publishing a weekly plan… a unique button on the featured plan: 'sign up and use this week'."* Design: a static page under `kitchenwizard.ai/this-week/` generated from a featured `MealPlanTemplate` by a script (SEO-indexable, no public API, pushed with the site), and **the claim in 3.4 also accepts a `templatePlanId`** — sign-up from that button adopts the template as the new account's this-week plan (the existing use-template path), or, at minimum, lands them on it in the app.

**3.8 Analytics.** Server-side funnel events keyed on the guest session: session created → wizard step reached (each) → generated · thin-shelf shown → plan opened → recipe opened → door tapped (which door) → sign-up started → sign-up completed → claimed; **plus sign-ups that never reached a plan, and the step where sessions stop** (Hans: *"if they sign up for the trial without getting to a plan, and where they drop out"*). No third-party analytics.

**3.9 Naming (proposal, Hans invited it — *"Try before you… trial? … test drive… test kitchen… there's something there"*).** Chat-Claude's pick: **"Test Kitchen"** — *"Take Kiwi for a spin in the Test Kitchen. No account, no card, no trial to trial."* It names the thing (a kitchen where you try before you commit), it's a noun the site can put on a button and in a URL (`/test-kitchen`), and it plays the trial joke without depending on it. Runners-up: *"Try before you trial"* as the headline over the button; *"Test drive"* (weaker — nothing about food).

**3.10 What this is NOT:** not the co-pilot (row 12); not web parity as a goal (the web renders what the app renders; whatever works, works); not a free tier — the trial rules stay Stripe's; **not an AI-invention surface** — that is the app's, behind sign-up.

## 7. Sibling: the Kiwi Cookbook on the web (SEO) — Hans asked whether it helps

Hans: *"once we get Kiwi Cookbook browsing ready we can display a web view of that so users can peruse the meals and hopefully that helps drive visitors and SEO (if it won't help, maybe we deprioritize it)."* **Chat-Claude's answer: it helps, more than any other thing on the marketing side, and slowly.** Public, indexable recipe pages are the largest organic-search asset a meal app can own — long-tail recipe queries are how Mealime, Plan to Eat and the rest get found — and the catalog (1,300+ meals, Kiwi's own, no licensing question) is exactly that asset sitting unused. The cheap version is not a web app: **a static generator that writes one page per catalog meal into the site** (title, image, ingredients, steps, cook time, `schema.org/Recipe` structured data, canonical URL, a "cook this in Kiwi" door), pushed like any other site change. It is also the guest's "peruse" surface for free. Payoff is measured in months, not weeks — which is the reason to start it early and the reason it never blocks product. **Proposed: its own roadmap row, built right after this funnel; deprioritize only if the site cannot host a few thousand static pages, which Netlify can.**

**8.5 The Cookbook pages (row 14) — the shape, ruled in the mockup:**
- **One page per dish FAMILY (parent), variants as a "three ways" section on the same page.** ~562 parents in the catalog. This is what stops seven baked-chicken pages competing with each other. Publish by parent popularity: an opening batch of ~100, then ~10/day automated (read-only DB role; GitHub Actions or Cloud Scheduler). The popular parents give the site credibility; the long tail is where a small site actually ranks.
- **Ingredients card is STICKY; steps run full length on the page.** No scroll box (hides half the recipe from Google, breaks print) and no stacking (wastes the width).

**8.6 Social cadence (chat-Claude's recommendation; channels not yet ruled).** About one post per day per platform, all of it drawn from content that already exists: the Friday plan, one recipe a day, one product post a week. ## 9. Phase 0 corrections — September 25, 2026 (read-only audit of the tree; the build follows THIS section where §3 differs)

**9.1 The guest lane persists NOTHING into the plan tables (supersedes §3.1's "the ids of what was generated" and §3.4's "re-parents… fork-on-acquire").** `meal_plan_instances.userId`, `meal_plan_templates.userId`, `user_preferences.userId` and `wizard_last_batches.userId` are NOT NULL (RESTRICT / CASCADE) — read from the schema, the migration SQL and the live DB. A guest never owns a plan row, never forks a meal (fork-on-acquire is a deep copy that fires at ACTIVATION, and a guest never activates), never has a preferences row. **The guest's plan is JSON on `GuestSession`** (`preferences`, `candidates`, `draft` — the draft in the exact shape `GET /wizard/drafts/:id` returns), and **the claim is a FIRST PERSIST for the new user**: `persistWizardDraft` + `activateWizardDraft` + `markFirstPlanCreated` inside the signup transaction. Rejected: a shadow `User` row per guest (collides with `authLimiter`, email uniqueness and the per-user `Subscription` row) and a nullable `userId` on the plan tables (touches a RESTRICT FK and every `where: { userId }`). → **D-WS9-259.**

**9.2 The thing to switch off is the live-slot gap-fill, not D-WS9-238.** D-WS9-238 is RULED and UNBUILT and appears zero times in `src/`. The built invention path is `lib/wizardExpansion.ts`'s `liveSlots` → `expandOneMeal`. The guard is `catalogOnly` on `ExpandCandidateOptions`, tested right after `liveSlots` is built, returning a new `catalog_only_gap` status **before any `runAICall`**. **9.3 Guest spend needs its own column and branch (amends §3.5).** `spendGuard.ts` early-returns on `userId == null` (BUG-262, system calls) and the global sum excludes null rows — a guest call attributed as null would be unguarded AND invisible. **9.5 The per-IP cap (§3.5) is not implementable until `TRUST_PROXY_HOPS` is measured.** It is UNSET on the service and has never been measured (DEPLOY.md:163-171 — "reasoned, not measured"); `req.ip` is Google's front end for every request, so a per-IP cap today is one global bucket. The existing `authLimiter` IS an IP-keyed limiter on anonymous routes — §2's "does not exist" was half wrong; it exists and is ineffective for the same reason.

**9.6 Smaller corrections.** `firstPlanCreatedAt` is the Home teaching-arc collapse signal read by `GET /home`, not the first-run gate (that is `onboardingComplete`); the claim calls the existing write-if-null helper. · The wizard chain (`wizard` → `plan-options` → `pick-meals` → `plan/[id]` → `meal/[id]`) is ALREADY outside `(tabs)` — no tab-bar hiding is needed; the only new route is the `/test-kitchen` entry, and the one line that unblocks a guest is a non-eviction branch in `sessionBootstrap.ts`'s `sessionGateShouldEvict` (a pure, testable function that has NO test file yet — Block 2 adds one). · CORS is a bare `cors()` (wildcard) at `app.ts:89`; it works for `app.kitchenwizard.ai` today because the client sends a Bearer header, not cookies — an allow-list is hardening, not a requirement. · Turnstile mounts on `POST /guest/session` ONLY — a signup-side check cannot exempt the native app safely (spoofable), so signup hardening stays BUG-222's product half. → **D-WS9-262.** · The claim path for `templatePlanId` is the existing `POST /plans/use-template/:templateId` plus activation. · A grocery list is NOT derivable from a template (lists FK to instances) — the weekly page's list is produced once by Hans's account and written into the page as content. · `AdminActionLog` does not exist; `UserActivity` cannot host guest events (NOT NULL `userId`, a 42-value enum) → a `GuestEvent` table with a plain-string `event`. · The limiters already key on `userId`, so a guest id in that slot gets its own bucket — no limiter rework. · Three names for one path (§3.6 `/try`, §3.9/§6 `/test-kitchen`, the site's comment) — **ruled: `https://app.kitchenwizard.ai/test-kitchen`**; the marketing site's Log in button → `https://app.kitchenwizard.ai/sign-in`; `expo-router.origin` moves to `app.kitchenwizard.ai` in Block 3, not before the store binaries are submitted (`app.json` is the contended file).

## 11. What the build changed — September 27, 2026 (Blocks 1b and 2; full text on D-WS9-263 / 264 / 268)

- **§9.6 was wrong about "the only new route is the `/test-kitchen` entry."** The guest funnel is FOUR new routes — `app/test-kitchen/{index, options, plan, recipe}` — because every existing plan screen is member-only on mount (`plan-options` streams over SSE and reads `/wizard/limits`; `plan/[id]` reads `GET /plans/:id`; `meal/[id]` reads as a user), and `getWizardDraft` has had no screen caller since D-WS9-191. Block 1's server comment about "the mobile draft screen" described a screen that no longer existed.
- **A guest's draft has no cooking steps** — finalize runs at save/activate, both doors. "Read the full recipe" (§3.2) is satisfied from the candidate's catalog meal: `sourceStoreMealId → GET /meals/:id` (public catalog meals only for a guest).
- **A guest token on a member route is a 401, never a 403** — and an authenticated 401 IS the session-expired cascade, so the client design is an allowlist of guest routes (`lib/guest/guestRoutes.ts`), not a 403 handler. `sessionGateShouldEvict` gained guest cases (its test file existed all along — §9.6's "has NO test file" was wrong).
- **The 409 at sign-up rolls the whole sign-up back** (stage 1 is inside the user-creating transaction), so the client resends once without the session and says the plan expired. `claimRetryable` keeps the session id for the next sign-in.
