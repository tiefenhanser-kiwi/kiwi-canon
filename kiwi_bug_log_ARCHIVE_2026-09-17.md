### BUG-236 — One email-change submit produces TWO requests 5 ms apart: two token mints, two provider sends

- **Date:** September 8, 2026 · **Surface:** mobile `app/(tabs)/profile.tsx` — `EditableRow`'s commit path, shared by the **email, name and phone** inline-edit rows; observed server-side at `POST /api/me/email/request-change` · **Found by:** Hans's device pass on `c38a596` (in the log he read as a clean pass — it was, for the thing it was testing).
- **Status:** ✅ **FIXED AND DEVICE-PROVEN — `452fa4e`, September 8, 2026** · **Priority:** **P2** · **Target:** Lane B mobile-client block · **Cross-ref:** BUG-224 · BUG-219 · BUG-227 · BUG-235 · BUG-237 (same file).
- **THE MEASUREMENT:** two `email_change_requested` events from **one** submit — req `id: 6` and `id: 7`, both `200`, response times **458 ms and 447 ms**, completing 6 ms apart. **Received about 5 ms apart and run concurrently. No human taps twice in 5 ms.**
- 🔴 **THE CAUSE, SETTLED BY READING THE FILE — NOT DEV-ONLY, THIS IS A REAL PRODUCTION BUG.** `EditableRow` wires **both** `onSubmitEditing={onCommit}` **and** `onBlur={onCommit}`, with `returnKeyType="done"`, `autoFocus`, and `blurOnSubmit` left at its **default of `true`**. One "done" tap fires `onSubmitEditing`; `blurOnSubmit` then blurs the field, which fires `onBlur`. **Two `onCommit` calls, milliseconds apart, from one tap.**
- 🔴 **THE AUTHOR ANTICIPATED IT AND THE GUARD CANNOT WORK.** `handleCommitEdit` calls `setEditingField(null)` and then returns early on `if (!editingField)` — but **`editingField` is a closure binding from the current render.** A state setter does not mutate the binding the already-scheduled second invocation is holding, so **both calls read `"email"` and both pass the guard.** ⚠️ **No `useState`-based guard can close a same-tick double-fire; this is a class of mistake, not a typo.**
- ✅ **STRICTMODE IS ELIMINATED — the §27 discriminator is no longer needed.** A grep across `app/`, `components/`, `lib/` and `contexts/` returns **no `StrictMode` anywhere**. The earlier plan was to settle this with a production build; **a static answer arrived first and is stronger, because it names the mechanism instead of only excluding one.** ⚠️ **The "every other request appeared once" counter-evidence was correctly refused as evidence either way (React Query dedupes in-flight QUERIES, not MUTATIONS).**
- 🔴 **SCOPE IS WIDER THAN FILED, AND THIS IS THE PART THAT CHANGES THE WORK.** `handleCommitEdit` is the shared commit handler for the **name and phone rows as well as email** — so **every inline profile edit double-PATCHes**, not just the one Hans happened to be watching in a server log. **Filed as an email bug; it is a profile-screen bug.**
- ✅ **RULED — THE FIX IS TO MAKE THE AUTHOR'S OWN GUARD WORK, BY BACKING `editingField` WITH A REF.** The guard's intent was right; only its state read was. Replacing that read with a ref written synchronously makes the existing early-return fire on the second call. 🔴 **NOT by dropping `onBlur` as a commit trigger:** `onBlur` is what commits an edit when the user taps away, and removing it would silently DISCARD edits — trading a duplicate request for lost user input, which is the worse defect. **Both triggers stay; the second call is swallowed.**
- 🔴 **WHAT IT COSTS ONCE EMAIL WORKS:** two verification emails per tap, two token mints, two billable provider calls. ⚠️ **AND THE WORSE ONE, STILL UNVERIFIED: if the route keeps a SINGLE pending email-change per user, the second mint invalidates the first — and the user clicks whichever email they see first, which would be the dead one.**
- ✅ **NOT A REGRESSION FROM `c38a596`.** The seam only made it VISIBLE by logging one line per send attempt.
- ✅ **BUILT AS RULED: `editingField` is now backed by a ref, and the author's own early-return works.** All three rows confirmed by reading — one `handleCommitEdit` passed as `onCommit` to the name, email and phone `EditableRow`s. **Every `editingField` state write has a paired ref write (start / cancel / commit), including `handleCancelEdit`, which is currently DEAD CODE with no call site** — mirrored anyway, because that is exactly the path that would silently break the invariant when someone wires a Cancel button later.
- 🔴 **AN ORDERING FINDING NOBODY SPECIFIED, AND IT WOULD HAVE REPRODUCED THE BUG THROUGH A DIFFERENT DOOR: the ref must be cleared BEFORE `Keyboard.dismiss()`, not after.** `Keyboard.dismiss()` blurs the focused input, which fires `onBlur` → `onCommit` and **re-enters the same handler**. Clearing afterwards would have left the re-entrant call reading a non-null ref and passing the guard. ⚠️ **Generalise it: any guard cleared around a call that can synchronously re-enter the guarded function must be cleared FIRST.**
- ⚠️ **A §27.3 INSTANCE, SELF-CAUGHT: a case-sensitive grep for `editingField` returned every READ and zero WRITES**, because `setEditingField` capitalises the E. **That list would have "confirmed" the ref invariant against a set containing none of the writes it was supposed to check.** Re-run case-insensitively. **The grep shape answered a narrower question than the one being asked — the same shape as the handler count that was off by a factor of fifty.**
- ✅ **DEVICE-PROVEN, Android (Google Pixel 10, Expo Go), September 8, 2026 evening: five consecutive `PATCH /api/me/profile` calls across name and phone at 27 s / 42 s / 19 s / 4 s human-scale spacing — NO 5 ms pair anywhere — and ONE `email_change_requested` where `c38a596` produced two.**
