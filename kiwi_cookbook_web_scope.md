## 1. What it is, in one paragraph

A **static generator**, not a web app. It reads Kiwi's own catalog (1,124 `batch_generated`, `isPublic` meals with images, ingredients, steps, macros — no licensing question) and writes one HTML page per meal into the site repo `C:\Cooking App\kiwi-site\cookbook\<slug>\index.html`, plus a browse index, cuisine hubs, a recipes sitemap and `schema.org/Recipe` JSON-LD on every page. A push to `main` is the deploy (Netlify). It publishes on a cadence — an opening batch, then a daily drip — so the site shows steady new content for months. Every page carries a **"Cook this in Kiwi"** door. It is the marketing asset with the longest payoff and the lowest risk: **nothing in it touches the app, the API, the production database, or the three frozen site pages.**

## 3. URLs and slugs — permanent by construction

- `kitchenwizard.ai/cookbook/` — the browse index (client-side filters over `cookbook/index.json`: cuisine, time, eating style tags, search box).
- `kitchenwizard.ai/cookbook/<slug>/` — one meal. Slug = the title, lower-case, ASCII, hyphens (`shrimp-scampi-over-angel-hair-pasta`); a collision appends the first 6 characters of the meal id.
- `kitchenwizard.ai/cookbook/cuisine/<cuisine-slug>/` — one hub per cuisine (Italian-American, Mexican, …), linking every published meal in it.
- **`scripts/cookbook/state/_slugs.json` is the source of truth for slugs** (v4: state lives under `scripts/`, force-404'd — the repo root is the document root, so anything under `cookbook/` is a live URL; the v1 placement would have published the pipeline) — the generator reads it first and only appends; a slug once published never changes, whatever happens to the title. Committed with the pages.
- Canonical on every page = its own URL; `robots.txt` unchanged for the cookbook (everything indexable).

## 4. The page

- **Head:** `<title>` = *"{title} — a {minutes}-minute {cuisine} dinner | Kiwi Cookbook"*; meta description = the catalog `description`; canonical; Open Graph + Twitter card with the meal image; the site's fonts and CSS (inlined from `index.html`'s style block, trimmed — no framework, no build step, the deploy guide's rule).
- **Body, in order:** breadcrumb (Kiwi › Cookbook › {cuisine} › {title}) · hero image (`loading="eager"`, width/height set) · title · one answer-first line — *"A {minutes}-minute {cuisine} dinner for {servings} — {calories} calories per serving."* · description · the macros strip (calories · protein · carbs · fat, "per serving, estimated") · **the door** (§6) · ingredients grouped by dish, lines through the ingredient-line rule (exact fractions, count units dropped, `(preparationNote)`, "optional" marked) · steps grouped by dish, numbered · "You might also like" — 4 meals, same cuisine first, then shared tags (published pages only) · the allergen / nutrition disclaimer (the app's text, `lib/legal.ts`) · footer with the site's links.
- **JSON-LD `Recipe`:** `name`, `image`, `description`, `recipeCuisine`, `recipeCategory: "Dinner"`, `totalTime` / `cookTime` (ISO 8601 from `minutes` / `activeTimeMinutes`), `recipeYield: "{servings} servings"`, `nutrition { @type: NutritionInformation, calories, proteinContent, carbohydrateContent, fatContent }`, `recipeIngredient[]` (the formatted lines), `recipeInstructions` as one `HowToSection` per dish holding `HowToStep`s, `keywords` (tags + cuisine), `author { @type: Organization, name: "Kiwi" }`, `datePublished` (the day it went live), `suitableForDiet` where a tag maps cleanly (vegetarian, vegan, gluten-free, low-carb, …). `BreadcrumbList` JSON-LD beside it. No `aggregateRating` (none exists; never invent one).
- **Print stylesheet** (recipes get printed) and a "Print" link. Pages are static HTML with no JavaScript required to read; the only script is the analytics tag.

## 5. Cadence and selection — the drip, ranked and interleaved (RULED, Hans, September 28)

Hans's constraint, verbatim: *"if we have popular meals that might get more search hits, we don't want to publish them all at once. and I don't want to start with random meals from only rows 1200+ that no one wants to cook. or if they search on web for a recipe they only get weird vegan stuff if we start with less popular stuff."* His sketch — publish ranks 1, 11, 21, 31… on day one, 2, 12, 22… on day two — is decile interleaving. The rule that implements it:

- **NO computed popularity score (Hans, v3):** *"I have been the only user and it's all test data with my preferences."* `useCount` / `likeCount` / `saveCount` / plan-inclusion counts are ignored. **The catalog's own row order IS the popularity ranking** — the target list was ranked when the catalog was built, and each popular dish was generated in several versions: *"Meal row 1 is the most popular and meal rows 2–7 are variations of meal row 1. meal row 8 is the second most popular meal and rows 9–14 are variations of that meal… the variation level tapers off."* The grouping key exists in the schema: **`Meal.dishFamilyKey`** (D-WS9-045, the slug of the target dish). **Family rank = the family's position in catalog order** (earliest `createdAt`; if inserts scrambled it, the store-fill harness's frozen 562-entry target list is the order). **Version index** = order within the family.
- **One version per family first, variations spaced:** the eligible list = each family's next unpublished version, but a family that already has a published page waits `FAMILY_SPACING_DAYS` (14) before its next; ordered by family rank. **Opening batch = version 1 of the families at ranks 1, 3, 5 … 199 — 100 distinct dishes** (never seven baked-chicken pages on day one; the even-ranked families' first versions arrive over the following days from decile 1). **Daily = 10: deciles over the eligible list by family rank, one from each** — a top-family dish and a tail dish every day; a popular family's variations trickle in weeks apart across the run. `COOKBOOK_DAILY_COUNT` and `FAMILY_SPACING_DAYS` are one constant each. Related-meals on a page link the family's other published versions first.
- **The full catalog takes ~100 days at 10/day** — a new page every day through the November 16 marketing start and the Thanksgiving push.
- **Automated from day one (RULED, D1):** a GitHub Action in `kiwi-site` on a daily cron (07:10 ET) runs the publisher, commits the new pages + rebuilt index / hubs / sitemap, pushes `main`; Netlify deploys. Hans's only act is watching Search Console. **Design so the site repo is self-contained:** the generator lives IN `kiwi-site` (`scripts/cookbook/*.mjs`, Node 20, one dependency `pg`, hand SQL against the few catalog tables — no Prisma, no checkout of the private app repo, no deploy key); the Action needs ONE secret, `COOKBOOK_DATABASE_URL` = a **read-only Neon role on the DEV branch** (Hans creates it in the Neon console; the catalog on dev is production's copy; a production read-only role is a post-approval swap because creating it touches production). `netlify.toml` pins `command = ""`, `publish = "."` so the new `package.json` never triggers a Netlify build. **Manual run is the same command** (`node scripts/cookbook/publish.mjs --count 10`) for the opening batch and for re-renders.
- **Nothing is pre-rendered into the served tree** — a staged page in the repo is a live URL, and Netlify serves the repo root. The queue file is data, not pages.
